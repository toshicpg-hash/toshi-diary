# まとめて同期と保存順序（1.2.42候補）

## 再現した原因

未改変main 16724f392d243703137dc6769bafade4763474cd（1.2.41）は `runner.run({concurrent:true,...})` で予定・日記・お金を同時に開始する。予定の大容量保存では `HubApp.commit` が `saving=true` の間にIndexedDB保存・読み戻し・localStorageポインタ更新を待つ。一方、お金の `captureComparison → financial → HubApp.checkWrite` も同じ保存ガードを確認するため、この時間帯に重なると停止する。

実アプリ・保存実装・同期処理と合成Google応答を使い、予定2651件、日記1件、お金134記録/165履歴（実績・消込・31件の編集履歴を含む）を設定。予定保存を700ms、日記保存を150ms、お金の状態読取りを180ms遅延させた。旧版は予定2651件と日記が成功し、お金だけ「同期失敗・未確認：保存中です。完了を待ってください」となった。実機内部の実行トレースは取得していないが、報告と同一結果になるコード上の競合を確認した。

## 修正

- まとめて同期を予定→日記→お金の順に実行し、各処理の保存・読み戻しを含むPromiseが完了するまで次へ進めない。
- `commit` の進行中保存Promiseを保持する。開始時・各ジョブ前に実Promiseをawaitし、「保存完了待ち」を表示する。保存が失敗すれば未完了として表示する。
- 先に始まっていたお金の同期・保全処理も完了まで待ってから、まとめて同期を開始する。別の予定操作が進行中なら開始を拒否する。
- まとめて同期中の書込みUIと追加の単独同期を抑止。お金の自動同期も重ねない。ジョブ終了後の確認記録処理では従来の書込み可否を戻し、確認記録送信の既存許可判定を妨げない。まとめて同期自体の多重開始防止は終了処理まで保持する。
- runnerは実行Promiseを登録してから状態通知を出し、通知中の再入でも同じ実行に合流する。
- 全ジョブの `ok===true` が揃う場合だけ全体成功を表示する。未設定/処理中による除外・保存失敗・認証取消・通信未確認を成功扱いしない。

`checkWrite` の保存中拒否は削除・緩和していない。保存中の実呼出しが拒否されるassertもある。金融の金額・実績・ID・履歴の計算/保存/通信アルゴリズム、Google認証scopeと権限、日記保存実装、HubPersistenceは変更しない。workerは版/cache参照準備のみ。
